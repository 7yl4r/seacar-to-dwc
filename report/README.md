# report

A small quarto website: one report page per SEACAR program the pipeline has processed,
plus a listing gallery. Structure follows the batch-generation pattern from
[quartobatch](https://github.com/7yl4r/quartobatch) -- a template + a generate script that
stamps out one `.qmd` per item, registered as a project `pre-render` step, plus a
`listing.qmd` that lists them -- reimplemented in Python since the rest of this pipeline is
Python rather than R.

- `template.qmd` -- the report layout. Reads
  `data/04_processed/<program_id>/{report_meta.json,raw_data_profile.json,event.csv,
  occurrence.csv,emof.csv}` and `datasets/<program_id>/{summary.md,transform_notes.md,
  archive_summary.md}` -- output the pipeline already writes, plus the human-editable writeups
  next to it -- so building the report never re-scrapes SEACAR, calls WoRMS, re-runs any
  transform, or calls out to an AI. It's a rendering of `datasets/<program_id>/README.md`
  (see the top-level README's "Documentation structure" section) -- both read the same
  underlying files, neither is a second source of truth.
- `mapping_reference.md` -- the standardized column-mapping writeup (Event/Occurrence/eMoF rules),
  identical across every dataset since the mapping is shared code; `template.qmd` and
  `case_study.py` both include it verbatim, under "Transformation & column mapping".
- `generate_reports.py` -- pre-render step (wired into `_quarto.yml`). For every program under
  `data/04_processed/` with a `report_meta.json`, fills in `template.qmd`'s `__PROGRAM_ID__` /
  `__TITLE__` / `__DESCRIPTION__` / `__DATE__` placeholders and writes `reports/<id>.qmd`; also
  copies that program's DwC-A zip into `reports/downloads/<id>/` so the report's download link
  resolves inside the built site. `reports/` is regenerated (deleted and rebuilt) on every
  render, so it's gitignored.
- `listing.qmd` -- quarto's built-in `listing` directive over `reports/`, giving a grid gallery
  keyed off each generated page's title/description/date front matter.

## What's generated where, and by whom

Each report pulls together content from different points in the pipeline, so a reviewer can
check each step rather than just the final archive:

| Section | Source | Generated by |
|---|---|---|
| Raw data summary | `datasets/<id>/summary.md` | AI-drafted, human-edited (see top-level README) |
| Raw data profile | `data/04_processed/<id>/raw_data_profile.json` | `profile.py`, every pipeline run -- deterministic |
| Transformation & mapping (standardized part) | `report/mapping_reference.md` | hand-authored once, shared by every dataset |
| Transformation & mapping (applied-to-this-dataset table) | `raw_data_profile.json` x `config/measurement_vocab.yaml` | computed at render/generation time |
| Transform review notes | `datasets/<id>/transform_notes.md` | AI-drafted, human-edited |
| Final archive summary | `datasets/<id>/archive_summary.md` | AI-drafted, human-edited |
| Species / measurements tables, validation charts | `event.csv`/`occurrence.csv`/`emof.csv` | `transform/*.py`, every pipeline run |

The three AI-drafted files carry a `reviewed: false/true` front-matter flag (alongside an
`instructions` field saying what each should cover -- no separate `*.instructions.md` sibling)
that `template.qmd` (and `datasets/<id>/README.md`) render as a warning banner until a data
manager signs off -- see the top-level README's "Documentation structure" section for the
workflow. Both parse that front matter the same way, via `seacar_to_dwc.reviewable_docs`.

## Why plain string substitution instead of quarto `params`

Quarto's `jupyter` engine (unlike `knitr`/R) doesn't auto-populate a `params` object from a
document's front matter -- that only happens through a papermill-style parameters cell used for
*overriding* a single file at render time, which doesn't fit "bake N separate static pages."
So `generate_reports.py` substitutes values directly into the `.qmd` text before quarto ever
sees it, same as `template.qmd`'s title/description/date.

## Local kernel gotcha

If `quarto render` fails with `No such file or directory: '.../myenv/bin/python'`, it's quarto's
Jupyter kernel autodiscovery picking up a stale `myenv` kernelspec left over from an unrelated
project (`jupyter kernelspec list` / `~/.local/share/jupyter/kernels/`), not anything in this
project. `_quarto.yml` pins `jupyter: python3` to work around it; if that kernel also goes
missing, register a fresh one with `python -m ipykernel install --user --name python3`.
